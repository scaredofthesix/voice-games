# Sprint 1 Reflection (Team 40)

## Learning points

- A small, strictly Must-Have MVP (five stories) was enough to get a clear customer
  acceptance. Keeping the scope minimal made the demo focused and the feedback concrete.
- Fixing the three concrete issues from the previous review (speed, recognition, placeholder)
  built visible trust faster than adding new features would have.
- Writing acceptance criteria and story points before the review made the backlog easier to
  discuss with the customer and exposed wording that needed tightening.

## Validated assumptions

- Voice-only control is engaging and understandable to the customer as a learning tool.
- Lenient, multi-attempt recognition is the right call: "do not lose on one mishearing"
  matched what the customer wanted for children.
- The customer is comfortable steering scope through MoSCoW and MVP labels, so investing in a
  clean, filterable backlog pays off.

## Friction and gaps

- GitHub lacks a native story-point field without a Project (v2) board, so estimates live in
  issue bodies and `docs/user-stories.md` for now.
- Recognition accuracy is still untested with real children's voices.
- We had no user story for built-in categories or for phrases even though both had been
  discussed - the backlog lagged the conversation.

## Planned response

- Build the MVP v2 Project board with Backlog and Sprint views once the `project` scope is
  enabled, and surface story points there.
- Add a recognition-accuracy test plan (target 80-90%) with child voice samples.
- Capture discussed-but-unwritten ideas as issues immediately (done this review: US-18, US-19,
  US-20, and the four-games tracker #54).
